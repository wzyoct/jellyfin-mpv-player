# Ember Player 完整改造方案

更新时间：2026-08-31

## 1. 结论

当前“登录后首页无内容、进入电影页黑屏”的首要原因不是样式，而是 Emby 接口契约写错：`GET /Users/{UserId}/Views` 的实际返回值是 `QueryResult_BaseItemDto`，媒体库数组位于 `Items` 字段中；当前主进程却把整个响应声明为 `EmbyItem[]` 并直接交给渲染层。渲染层随后调用 `views.value.find(...)` 时会产生运行时异常，首页加载中断；电影页又因为没有有效的 `activeViewId` 提前返回，只剩深色背景。

这个结论与 Emby 官方接口文档一致：该接口的 200 响应为 `QueryResult_BaseItemDto`，包含 `Items` 和 `TotalRecordCount`。参考：<https://dev.emby.media/reference/RestAPI/UserViewsService/getUsersByUseridViews.html>

此外还有三个会继续制造空白页的问题：

1. `goLibrary()` 只有在 `libraryItems` 为空时才加载；首页只要曾加载过任意媒体库，切换“电影/剧集”就只在旧数据上做前端过滤。
2. 首页默认使用 `views[0]`，它不一定是电影库；多个电影库、剧集库或混合库都没有正确映射。
3. 页面只有一个共享 `isLoading` 和零散错误提示，没有可靠地区分首次加载、刷新、空数据、权限错误、离线和旧数据，因此失败后容易表现为纯黑背景。

## 2. 改造目标与验收标准

### 功能目标

- 已保存会话和新登录两条路径都能稳定进入首页。
- 首页至少显示“继续观看、最近加入、媒体库入口”中实际有数据的部分；全部为空时显示明确空状态。
- 点击“电影”只请求并展示电影，点击“剧集”只请求并展示剧集；切换媒体库后数据与标题同步更新。
- 所有请求失败都在对应页面显示可重试错误，不出现无说明黑屏。
- 详情、海报、音轨、字幕和 MPV 播放失败互不拖垮主页面。

### UI 目标

- 定位为桌面媒体工具，而不是营销落地页：内容优先、导航稳定、信息密度适中。
- 第一视口能识别当前页面、当前媒体库、加载状态和可执行动作。
- 保持电影感的深色基底，但减少大面积纯黑和单一红色；海报和背景图成为主要色彩来源。
- 1024 x 680 到 1920 x 1080 均无文字截断、控件重叠或布局跳动。

### 工程目标

- Emby 响应类型只有一个来源，IPC 两侧不再复制互相漂移的接口。
- 关键状态转换和数据映射有自动化测试。
- 每个阶段单独提交并推送，能够精确回滚。

## 3. 分阶段实施

### 阶段 1：先恢复可用性

影响文件预计为 `electron/emby.ts`、`electron/preload.ts`、`src/types.ts`、`src/App.vue` 和新增测试。

1. 新增通用 `QueryResult<T>` 类型，让 `getViews()` 按真实响应读取并返回 `result.Items`。
2. 在 IPC 边界对 `Items` 做最小结构校验；格式错误时抛出包含接口名称的明确错误，不做静默空数组回退。
3. 删除 Electron 主进程中重复的 `EmbyItem`/`PlaybackInfo` 结构，改为共享契约或明确的服务端 DTO，防止类型再次漂移。
4. 修正首页初始化顺序：先取得并校验媒体库，再选择兼容的默认库，最后并发加载首页内容。
5. 修正电影/剧集导航：每次筛选改变都按服务端 `IncludeItemTypes` 重新请求；媒体库选择只是额外 `ParentId` 条件，不再依赖旧数组前端过滤。
6. 首次加载失败时清空不适用数据并保留错误；刷新失败时保留旧数据并标记“刷新失败”，避免真假空状态混在一起。

验收：登录、重启恢复会话、首页、电影、剧集、切换媒体库、刷新七条路径均能得到内容或可解释状态。

建议提交：`fix: 修复 Emby 媒体库响应与页面加载`

### 阶段 2：统一页面状态和数据流

1. 将单一 `isLoading` 拆为 `homeState`、`libraryState`、`detailState`、`searchState`，每个状态包含 `status`、`data`、`error` 和必要的刷新标记。
2. 为首页和媒体库请求增加递增请求序号；快速切换页面或媒体库时，只允许最后一次请求写入 UI，避免旧响应覆盖新页面。
3. 明确四类页面状态：骨架屏、正常内容、无内容、错误与重试。搜索增加“正在搜索”，不再把请求未完成显示成“没有结果”。
4. 把 28 KB 的 `App.vue` 按职责拆为页面和领域组件：`HomePage`、`LibraryPage`、`MediaCard`、`MediaDetailDialog`、`ConnectionSettings`，数据请求集中在组合函数中。
5. 组件只消费已归一化的领域模型，不直接理解 Emby 原始响应。

验收：模拟慢请求、接口报错、空媒体库和快速连续切换时，页面不会闪回、误报空数据或保留错误内容。

建议提交：`refactor: 统一媒体页面状态与数据流`

### 阶段 3：重做视觉与交互

#### 信息架构

- 顶栏保留“首页、电影、剧集、搜索、设置”，当前页面使用稳定的底边或背景状态，不依赖微弱颜色差异。
- 首页顶部使用实际媒体背景图作为焦点，但控制在首屏约 55% 高度，让下一内容区露出；没有背景图时使用中性占位，不使用纯黑空区。
- 首页内容顺序固定为：继续观看、最近加入、媒体库。不存在的数据区整段隐藏，全部为空时显示带刷新和设置入口的空状态。
- 媒体库页标题、数量、媒体库选择和排序放在同一工具栏；卡片区域使用稳定网格，不让图片加载改变尺寸。

#### 视觉系统

- 背景分为窗口底色、内容层和交互层三个中性色阶；红色只用于主操作、播放和焦点，不铺满导航与卡片。
- 字体字号按桌面工具收敛：页标题约 28-36 px，区块标题 18-22 px，卡片标题 13-14 px；不使用随视口缩放的字号。
- 卡片圆角不超过 6-8 px；工具按钮使用 Lucide 图标和 tooltip；二元设置使用开关，选项集合使用菜单或分段控件。
- 海报固定 `2:3`、背景图固定 `16:9`，骨架、占位、加载完成都占据同一尺寸，消除布局跳动。
- 使用 Emby 自身海报和背景图作为主要视觉资产，避免额外的装饰渐变、光球或与内容无关的插画。

#### 交互细节

- 媒体卡片增加清晰 hover/focus 状态、观看进度和类型/年份辅助信息；键盘焦点必须可见。
- 详情改为大屏侧栏或受控对话框，关闭按钮固定可见，背景图失败不影响正文和播放按钮。
- 搜索使用带状态的覆盖面板：输入、防抖、加载、结果、无结果、错误各自独立。
- 设置页直接服务于连接任务，去掉占据大量空间的营销式文案；服务器、账号、MPV 路径和连接状态分组展示。

验收：分别在 1024 x 680、1440 x 900、1920 x 1080 截图检查；覆盖长中文/英文片名、无图、空库、错误弹层和搜索结果，确认无重叠、溢出和不可读文本。

建议拆成两个提交：

- `feat: 重做首页与媒体库界面`
- `feat: 优化详情搜索与设置交互`

### 阶段 4：图片、播放和稳定性加固

1. 当前图片以 base64 字符串同时缓存在主进程和渲染层，且 `imageCache` 无上限。改为有容量限制的 LRU 缓存，或注册只读自定义协议直接流式返回图片，避免长期浏览后内存持续增长。
2. 为图片请求设置尺寸、超时和失败状态；海报失败只影响单卡片，不产生全局错误。
3. 播放前校验 MPV 可执行文件并给出可操作错误；区分“无法启动、无播放源、网络失败、字幕失败”。
4. 检查 `DirectStreamUrl`、鉴权头、外部字幕和恢复进度在实际 Emby 版本上的兼容性。
5. 为主进程增加脱敏日志：记录接口名、状态码和耗时，不记录密码、访问令牌或完整播放 URL。

验收：连续浏览大量海报后内存趋于稳定；MPV 缺失、视频源不可用、字幕失败和播放结束都能正确反馈且不影响继续浏览。

建议提交：`fix: 加固图片缓存与 MPV 播放错误处理`

### 阶段 5：测试、打包与发布基线

1. 单元测试：服务器 URL 归一化、`QueryResult` 校验、媒体库选择、筛选参数、状态转换和过期响应丢弃。
2. 组件测试：首页加载/空/错、媒体库加载/空/错、搜索状态、详情无图和长标题。
3. Electron 集成测试：mock preload API，覆盖登录后加载、页面切换、详情和播放调用参数。
4. 真实环境冒烟：使用用户的 Emby 账号完成登录、重启恢复、浏览、搜索、详情、播放、暂停退出和进度同步。
5. 依次运行 `npm run typecheck`、测试命令、`npm run build`、`npm run dist`；安装包仅作为发布附件，不进入 Git。
6. 版本从 `0.1.0` 提升到合适版本并创建带说明的 Git 标签。

建议提交：`test: 覆盖登录后媒体浏览主流程`

## 4. 建议实施顺序与回滚点

| 顺序 | 交付结果 | 必须通过的验证 | 回滚粒度 |
| --- | --- | --- | --- |
| 0 | 当前代码基线入库 | 类型检查、构建 | 初始提交 |
| 1 | 首页和电影/剧集可正常加载 | 契约测试、真实 Emby 冒烟 | 功能修复提交 |
| 2 | 页面状态可靠、结构可维护 | 状态与组件测试 | 数据流重构提交 |
| 3 | 首页/媒体库视觉完成 | 三档桌面截图与交互检查 | 两个 UI 提交 |
| 4 | 图片与播放稳定 | 内存、失败路径、MPV 冒烟 | 稳定性提交 |
| 5 | 可发布版本 | 全量检查与打包 | 版本标签 |

功能修复必须先于 UI 重做。否则视觉代码会建立在错误的数据契约上，黑屏问题仍会反复出现，并增加定位成本。

## 5. Git 工作方式

- `main` 始终保持可构建；每个阶段使用独立分支，例如 `fix/library-loading`、`feat/ui-redesign`。
- 每完成一个可验证阶段就提交并推送，不等到所有工作结束才留一个大提交。
- 提交前固定执行：针对性测试 -> `npm run typecheck` -> `npm run build` -> `git diff` 检查。
- 不提交 `node_modules`、`dist`、`dist-electron`、`release`、日志、`.env`、令牌或本机设置。
- 阶段完成后可建立标签，例如 `baseline-2026-08-31`、`v0.2.0`，用于快速回档。
